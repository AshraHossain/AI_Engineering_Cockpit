# ORION Phases 0–1 Implementation Plan

> **For agentic workers:** This plan is **not** for autonomous execution. The
> project author is writing the implementation code by hand as a learning
> exercise; Claude supplies the tests and reviews the result. Do not implement
> the tasks in this plan with a subagent unless the author explicitly asks for
> that. See "How this plan differs from the standard format" below.

**Goal:** Stand up the `15-orion-alert-triage` project skeleton, then build the
dynamic tool registry and the four simulated KYC tools it serves.

**Architecture:** A `Registry` holds one immutable `ToolSpec` per tool — name,
description, JSON schema, callable, and the alert fields that tool is permitted
to receive. Tools are plain functions returning plain dicts, with one built by a
factory so it can be scripted to fail. Nothing in these two phases touches the
Anthropic SDK or the network.

**Tech Stack:** Python 3.11, uv, pytest, pytest-cov, ruff. No runtime
dependencies used in Phase 1 (`anthropic` is declared for Phase 4).

**Spec:** `docs/superpowers/specs/2026-09-16-orion-alert-triage-design.md`

## How this plan differs from the standard format

The writing-plans format requires every step to show the code. This plan shows
**every test in full** but deliberately **does not show the implementation
bodies**. Each implementation step instead gives the exact signature, the
docstring contract, and the behaviour the tests demand.

That is not a placeholder — it is the point of the exercise. The author asked to
write the implementation code and be coached, so handing over the bodies would
defeat the purpose. Anyone executing this plan who is *not* the author should
stop and ask first.

## Global Constraints

Copied from the spec and from the conventions of the existing cockpit projects:

- Python `>=3.11`; `.python-version` pins `3.11`.
- `[tool.uv] package = false` — application, not a library.
- Runtime dependencies: `anthropic`, `python-dotenv`. Nothing else.
- Dev dependencies: `pytest>=8.0`, `pytest-cov>=5.0`.
- Flat layout: `src/` and `tests/`, with `tests/conftest.py` putting `src/` on
  `sys.path` (the cockpit projects are not installed packages).
- Every module starts with `from __future__ import annotations`.
- Full type hints; Google-style docstrings with `Args:` / `Returns:` /
  `Raises:` sections, matching `projects/03-multi-model-orchestrator/`.
- No test may perform network I/O or require an API key.
- Lint with the repo-root config: `uv run ruff check --config ../../config/ruff.toml .`

## File Structure

| File | Responsibility |
|---|---|
| `pyproject.toml` | Project metadata, dependencies, uv and ruff config |
| `.python-version` | Pins 3.11 |
| `README.md` | What ORION is, how to run it |
| `alerts/alert-001.json` | The single input fixture: one flagged transaction |
| `src/registry.py` | `ToolSpec` and `Registry` — the dynamic tool registry |
| `src/tools.py` | The four simulated tools, their errors, and `build_registry()` |
| `tests/conftest.py` | Puts `src/` on the path; provides the `alert` fixture |
| `tests/test_scaffold.py` | Proves the fixture loads and the layout works |
| `tests/test_registry.py` | Registry behaviour |
| `tests/test_tools.py` | Each tool's contract, including the scripted failure |
| `tests/test_build_registry.py` | The assembled registry and its permission scopes |

**Why `src/tools.py` rather than a `tools/` package** (the spec says `tools/`):
four functions of roughly thirty lines each come to one readable module. A
package of four single-function modules plus an `__init__.py` is four times the
files for no gain in isolation, and they change together. If a tool later grows
a real HTTP client, split then. Flagged as a deviation at the end of this plan.

```python
"""Tests for the dynamic tool registry.

No tool is actually executed here — the registry's job is to hold specs and
render them, not to run anything. Callables are stand-ins.
"""

from __future__ import annotations

from typing import Any

import pytest
from registry import Registry, ToolSpec


def make_spec(name: str = "sanctions_screen") -> ToolSpec:
    """Build a throwaway spec for registry tests."""
    return ToolSpec(
        name=name,
        description=f"description of {name}",
        input_schema={"type": "object", "properties": {}, "required": []},
        run=lambda **kwargs: {"ok": True},
        allowed_fields=frozenset({"customer.name"}),
    )


def test_tool_spec_carries_its_permission_scope() -> None:
    spec = make_spec()

    assert spec.name == "sanctions_screen"
    assert spec.allowed_fields == frozenset({"customer.name"})
    assert spec.run() == {"ok": True}


def test_tool_spec_is_immutable() -> None:
    """A spec is configuration, not state.

    Phase 3 keeps credibility scores in their own store precisely so that
    nothing mutates a spec mid-run; freezing it makes that impossible rather
    than merely discouraged.
    """
    spec = make_spec()

    with pytest.raises(Exception):
        spec.name = "something_else"  # type: ignore[misc]
```

- [ ] **Step 3: Write the implementation — yours to write**

In `src/registry.py`, define a frozen dataclass `ToolSpec` with exactly these
fields and types:

| Field | Type | Meaning |
|---|---|---|
| `name` | `str` | Unique tool name; what the model calls |
| `description` | `str` | What the tool does; the model reads this |
| `input_schema` | `dict[str, Any]` | JSON Schema for the tool's arguments |
| `run` | `Callable[..., dict[str, Any]]` | The callable that does the work |
| `allowed_fields` | `frozenset[str]` | Dotted alert paths this tool may receive |

Hints, not code: `dataclasses.dataclass` takes a `frozen=True` argument, and
`Callable` comes from `collections.abc`. Module docstring and a class docstring
with an `Attributes:` section, per the repo convention.

Ask yourself before moving on: why `frozenset` rather than `set` for
`allowed_fields`? (A frozen dataclass containing a mutable set is only
shallowly frozen — the set could still be mutated in place.)

```python
def test_registry_starts_empty() -> None:
    assert len(Registry()) == 0
    assert Registry().names() == []


def test_registry_is_built_from_an_iterable_of_specs() -> None:
    registry = Registry([make_spec("alpha"), make_spec("beta")])

    assert len(registry) == 2
    assert registry.names() == ["alpha", "beta"]


def test_names_are_sorted_so_the_tool_list_is_stable() -> None:
    """Prompt caching keys on an exact prefix, and the tool list is part of it.

    A registry that returned tools in insertion order would silently change
    the cached prefix whenever registration order changed.
    """
    registry = Registry([make_spec("zulu"), make_spec("alpha")])

    assert registry.names() == ["alpha", "zulu"]


def test_a_tool_can_be_added_while_the_system_runs() -> None:
    registry = Registry([make_spec("alpha")])

    registry.add(make_spec("beta"))

    assert registry.names() == ["alpha", "beta"]


def test_adding_a_duplicate_name_is_refused() -> None:
    """Two tools with one name means the model's call is ambiguous."""
    registry = Registry([make_spec("alpha")])

    with pytest.raises(ValueError, match="alpha"):
        registry.add(make_spec("alpha"))


def test_a_tool_can_be_removed_while_the_system_runs() -> None:
    registry = Registry([make_spec("alpha"), make_spec("beta")])

    registry.remove("alpha")

    assert registry.names() == ["beta"]


def test_removing_an_unknown_tool_is_an_error() -> None:
    with pytest.raises(KeyError, match="ghost"):
        Registry().remove("ghost")


def test_get_returns_the_spec() -> None:
    spec = make_spec("alpha")

    assert Registry([spec]).get("alpha") is spec


def test_get_on_an_unknown_tool_is_an_error() -> None:
    with pytest.raises(KeyError, match="ghost"):
        Registry().get("ghost")
```

- [ ] **Step 3: Write the implementation — yours to write**

Add a `Registry` class to `src/registry.py`:

- `__init__(self, specs: Iterable[ToolSpec] = ()) -> None` — store specs keyed
  by name. Route through `add` so the duplicate check applies to construction
  too, rather than writing the check twice.
- `add(self, spec: ToolSpec) -> None` — raise `ValueError` naming the tool if
  it is already registered.
- `remove(self, name: str) -> None` — raise `KeyError` if absent.
- `get(self, name: str) -> ToolSpec` — raise `KeyError` if absent.
- `names(self) -> list[str]` — sorted.
- `__len__(self) -> int`.

Note on the default argument: `specs: Iterable[ToolSpec] = ()` uses an empty
tuple, not `[]`. A mutable default is shared across every call — a classic
Python trap worth knowing by hitting it rather than by being told.

```python
def test_adverse_media_search_times_out_on_the_first_call() -> None:
    search = make_adverse_media_search()

    with pytest.raises(ToolTimeoutError):
        search(name="Marek Dvorak", country="CZ")


def test_adverse_media_search_succeeds_on_the_retry() -> None:
    """The failure is transient — this is what makes a retry worth trying."""
    search = make_adverse_media_search()

def test_failure_count_is_configurable() -> None:
    """Phase 3 needs a tool that always fails to drive a score to the floor."""
    search = make_adverse_media_search(fail_times=3)

    for _ in range(3):
        with pytest.raises(ToolTimeoutError):
            search(name="Marek Dvorak", country="CZ")
    assert search(name="Marek Dvorak", country="CZ")["adverse_count"] == 2


def test_a_never_failing_instance_can_be_built() -> None:
    search = make_adverse_media_search(fail_times=0)

    assert search(name="Marek Dvorak", country="CZ")["adverse_count"] == 2


def test_each_instance_counts_its_own_failures() -> None:
    """State must live in the instance, not in the module.

    A module-level counter would leak between tests and between runs: the
    second test to call it would get a pass where it expected a failure.
    """
    first = make_adverse_media_search()
    second = make_adverse_media_search()

    with pytest.raises(ToolTimeoutError):
        first(name="Marek Dvorak", country="CZ")
    first(name="Marek Dvorak", country="CZ")

    with pytest.raises(ToolTimeoutError):
        second(name="Marek Dvorak", country="CZ")
```

- [ ] **Step 3: Write the implementation — yours to write**

In `src/tools.py`:

- `class ToolTimeoutError(RuntimeError)` with a docstring saying it stands in
  for a transient network failure.
- `make_adverse_media_search(fail_times: int = 1)` — a factory returning a
  closure that keeps its own call count.

This is the one stateful tool, and a factory is why: state lives in the closure,

## Deviations from the spec

Both need the author's agreement; the spec gets amended to match whatever is
decided.

1. **`src/tools.py` instead of a `tools/` package.** Four functions of about
   thirty lines each, changing together, in one readable module. Revisit when a
   tool grows a real client.

2. **Credibility scores are not stored on `ToolSpec`.** The spec says the
   registry entry holds the tool's current score. This plan freezes `ToolSpec`
   as pure configuration and leaves scores to the Phase 3 store, keyed by tool
   name — which is how they are persisted to JSON anyway. Reason: a spec that
   mutates mid-run is a spec that can be mutated by accident, and the score is
   state with a completely different lifecycle from the tool's identity.
   `test_tool_spec_is_immutable` encodes this decision, so reversing it means
   deleting a test on purpose rather than drifting.
